2. API rules that will save you debugging time
1. Use your own private app token. Our 500+ workflows share one token and already brush against HubSpot's 190 requests per 10 seconds limit. A separate app keeps your sync and our automations from throttling each other, and lets you see your own call logs.
Done 
   *    2. The child's identity fields are in HubSpot's sensitive-data tier. Child First Name phi_first_name__cloned_, Last Name phi_last_name, Gender phi_gender, Date of Birth phi_date_of_birth, Insurance IDs insurance_id_1 to insurance_id_4, Policy Holder DOB phi__policy_holder_dob, and Diagnosis phi_diagnosis only come back if the app has the sensitive-data scope for deals (crm.objects.deals.sensitive.read, plus .write if you ever write them). Without it they are silently missing from the response.
See #11


   3. Send internal option values, not labels. Several dropdowns have a value that differs from what staff see. Examples: Case Status shows "Active" / "Inactive" but stores Warm / Cold; Entered Client in CR shows "Yes- Completed" but stores Yes; NY Medicaid - Status shows "Credentialed" but stores Credentialing; BT Entered in Central Reach shows "Yes - Active" but stores Yes; LBA Licensure - NY shows "Will Apply" but stores No; Allergies shows "Yes" / "No" but stores Confirmed / Denial. The appendix lists every mismatch on the fields in this map.



   4. Many fields are read-only to the API. Calculated and synced fields reject writes (the whole PATCH fails). On Case: Location location, the staff name fields (supervising_bcba_name, current_primary_bt, current_primary_bt_2), Referral Source referral_source and the total-hours fields. On BCBA and BT: the home address, home city/state/zip, phone and BT gender fields mirror the linked Contact. Everything you write should go to a field flagged writable in this document.



   5. Staffing is associations, not fields. Who the Supervising BCBA or Primary BT 1 is lives on the Case to BCBA and Case to BT associations (section 4). Read them with the v4 associations API.



   6. Care Coordinator is the Case owner. hubspot_owner_id holds an owner ID. Resolve it to a name and email with GET /crm/v3/owners/{id}

.
   7. One property has a typo in its internal name: Ongoing Auth period end date is ongoing_autrh_period_end_date.
   8. Ignore the "F" twins. Fields ending in _f (for example ongoing_auth_period_start_date_f) are the upcoming-auth copies staff fill before a new auth starts. Map the plain field unless Sara wants CR to see the next auth early.


   9. Date fields come back as YYYY-MM-DD and must be written as midnight UTC.



   10. HIPAA rule on outbound messages: United Care never puts a child's full name in an email or message; staff use Case Initials case_initials. This only matters if anything you build sends notifications.
   11. A missing property breaks the whole write. If your code writes to a property that is later renamed or archived, HubSpot rejects the entire call. Tell us which properties your integration writes and we will protect them in future clean-ups.

Simple explanation
               * Webhooks provide speed. One ongoing-update workflow per entity sends record ID and object type when supported source properties change. Keep the three initial enrollment workflows separate.
               * Polling provides backup coverage. Recheck linked records and dependencies without stage or original-checkbox restrictions. Test coverage before enabling or reducing polling frequency.
               * Azure owns the complete comparison. Centralize mapped values, metadata, labels, explicit blanks, and required relationships in the mapping/comparison configuration. Workflow signals wake that process; they do not duplicate the entire comparison.
               * Use workflow triggers, not segment membership, for repeated change signals. A record can remain in a segment through multiple edits without another entry event.


Latest decisions and boundaries
               * Sandbox first. Create three ongoing-update workflows as inactive drafts, then test. No production rollout is authorized.
               * User-provided receiver: https://centralreachserverless-hffge8hxdxh6apd9.eastus2-01.azurewebsites.net/api/hubspot-webhook. Verify sandbox routing and signing configuration before testing; never paste secrets into chat.
               * Eligibility: CentralReach ID is known; no pipeline, stage, active-status, or original-gate restriction. ID availability is not proof of complete prior sync.
               * Contact-derived data: intended end state is Guardian and BCBA personal-contact values exposed through Case Property sync fields. Their existence, source associations, and event behavior still need verification. Read them only; do not write synced destinations. Retain direct related-record retrieval where those fields do not supply the required data.
               * Staffing: compare record IDs and association role labels, not just names or emails. Test association removals, replacements, and relabeling separately.
               * Audit: production Case History Log exists and can associate to all three entities. Reuse it for meaningful updates/failures only after verifying its sandbox equivalent and category choices. Do not use it as a detector or store raw patient/staff values in notes.


Minimum changes and tests before production
Extend existing hashes/comparisons to cover the complete mapped state; address poller stage restrictions, employee timestamp shortcuts, skipped blank metadata, and rapid-notification loss. Distinguish an intentional blank from a failed or unauthorized read. A Sensitive Data request without required scope can return 403; never convert that failure into destination clears. Test repeated edits, clears, inactive transitions, calculated and sync-property updates, related Contact edits, staffing changes, duplicate/reordered notices, concurrent webhook/poller runs, and partial failures. Save the successful comparison baseline only after the required writes succeed, preserving retries without duplicate record creation.


Benefit: faster updates with one maintainable comparison process.


Trade-off: comparison requires HubSpot reads; fewer CentralReach writes does not automatically mean fewer HubSpot API calls.
