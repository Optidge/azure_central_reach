### Why the queries were rejected

Neither the author nor the independent review saved the text of the six rejected queries (the independent review also had 6 of 11 rejected), so the six checks below are reconstructed from the rows that stayed open. The causes were reproduced live:

1. **KQL double-quoted strings inside the inline `--analytics-query "..."` argument.** The shell ends the argument at each inner `"`, so the query reaches Azure with its string quotes stripped. The saved stitching block (`kv` and `calls` in every file under `scripts/sandbox/kql/`) is full of `"..."` and `@"..."` strings and its `isPart` regex holds `""` and a backtick, so any inline copy of it is mangled. Reproduced: `print v = strcat(@"x", "y")` passed inline → rejected.
2. **KQL keywords used as column names.** A CR-call count naturally writes `extend kind = tostring(c.kind)`; `kind` is a keyword. Reproduced: `print c = 1 | extend kind = 'lookup'` → rejected. In this run a draft with summary columns `n`, `first`, `last` was also rejected and ran once they were renamed `calls_n`, `firstSeen`, `lastSeen`.
3. **The CLI hides the reason.** `az` reports every KQL parse error as `BadArgumentError: The request had some invalid properties` with no rows and no detail: the same text as the wrong `--app centralreachserverless -g …` form, so a syntax error looks like a connection problem.

**Fix:** write the KQL to a file and pass it with `--analytics-query @<absolute path>`. It is still one plain `az` command (no pipe, redirect, `;`, variable or `$(...)`), no quoting is needed, and it is the form the saved files' own usage lines give. Keep `--offset` covering the window (`3d` here, `30d` for query 5) and avoid keywords as column names (`kind`, `sample`, `rows`, and here `n` / `first` / `last`). Use `callKind`-style names.

**Saved KQL files:** all four were run unchanged with `@<path>` and `--offset 6h`: `errors-retries-deadletters.kql` (2 rows: the 2026-11-24 15:16:38 `workday_id differs` warning and a 15:19:44 host `ConnectionAbortedException`), `pipe-check.kql` (the 5 sweep records), `run-summary.kql` (the 5 sweep runs), `record-timeline.kql` (placeholder ID, 0 rows). None is broken; none was edited.

**Stitching limit seen (not a syntax fault):** when two log calls of one worker process interleave, the stitch merges them. The BCBA 67208227438 run summary at 2026-11-23 19:10:01.66 and 3 of the 7 retry calls lost their keys this way (the R4 BCBA's `workday_id differs` warning lands inside its summary). Counts by key can therefore undercount until Pkg item 13 (one-line JSON log) is built.
