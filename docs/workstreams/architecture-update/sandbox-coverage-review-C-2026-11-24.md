## Summary

The run sheet is close, but it is **not safe to start as written**. Five things block a run:

1. **The R1/R4 first runs are not `noop`.** The pending build changes `MAPPING_VERSION` (`stage3-2026-11-20` → `stage7-2026-11-23`, `src/lib/mappedState.mjs:7`). Every linked record's first run is therefore a full re-send, with every field in `changedFieldNames`. Matrix B5/T2 (M L238, L262) and `round-1-log.md` L180 say to stop on "an update with `dateOfBirth` in `changedFieldNames`". That rule produces a false stop at S1/S2.
2. **The gate window skips the label retry of every create.** With both gate settings set, the path follows the HubSpot CR ID (`syncEligibility.mjs:58-62`). Every create's 150 s label-confirmation retry is then `skipped gate: update` (`clientSyncWorkflow.mjs:369-396`, no bypass for retries), and HubSpot keeps `error CR_LABEL_POST_UNCONFIRMED`. Phase one in production has the same behaviour unless the "promote after create" workflow ticks the updates box first. That workflow is neither built nor tested in the sandbox. The run sheet ticks the box by hand (S3d).
3. **S6a stacks several failures on one record in one push.** On the R1 BCBA, `test_record` (U-29), an unreadable `personal_email` (B9) and a Workday mismatch (U-24) are set together. On the R1 Case, an unreadable Guardian phone (C8) and the "BCBA" supplier (U-14b) are set together. The first check that fails hides the others, so U-24, B9-unreadable and U-14b are lost.
4. **Hand-made records with several legs can create unplanned CentralReach records.** R2-30/X02-1, X04-3 and R3-5/X03-1 change one missing field at a time. If a field is filled before the next one is blanked, the record is complete for a moment, with Entered = Yes and the creates box ticked. That is a real CentralReach create.
5. **No check that the deployed code is the pending build.** S1 must not start until it is confirmed (SU-1 says "deployment hash" but gives no method). Stop rule 4 is also too narrow: with webhooks live, `--write` under `655b385` can send the `dob` decoy (1975-03-09) even with the poller off.

**Paths.** Path attribution needs fixing. On 2026-11-23 the sandbox webhook came about 9 minutes after the edit (`round-1-log.md` L148), and the poll runs every 5 minutes. So with both on, the poller usually runs first. The "first-run `source`" rule (RS L46) would then report false trigger gaps, and the only create-by-webhook proof (CO, S3a) can end up created by the poller.

**Estimates.** Calls: about 1,100 to 1,400, not 900 (the `check-cr-record` GETs, about 200, are left out). Hands-on time: about 9 to 11 h, not 6.5 h. The 2 days can become 1 long day plus a 30-minute check the next morning.
