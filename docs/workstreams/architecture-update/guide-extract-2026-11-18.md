- Sync status values (Zeke, for now): last_sync_status is success, error or waiting. error means a person needs to act; it is the failures report. waiting means the record is held on purpose, with the reason in last_sync_error, for example while CR still holds the temporary ID; it is not retried and never goes to the dead-letter queue. The value blocked is retired. Code today still writes blocked and noop until this is built.

- ID mismatch (Zeke, for now): when a linked record's HubSpot ID and the ID CR holds are both filled and differ, the integration makes no CR write and marks the record error. Employee: workday_id against CR External System ID. While CR still holds the record's temporary HubSpot record ID, the record is waiting, not error, until External System ID (Workday) is ticked in the CR checklist. Case: the HubSpot record ID against the CR client's External System ID. 11/18 — Zeke: temporary External System ID, status and update rules. They are the same for BT/RBT and BCBA, and they replace the wording above and in the architecture tab where they differ. (1) A create that sends the HubSpot record ID as the temporary ID ends with last_sync_status = waiting and the reason "Waiting for the Workday ID". A create that sends workday_id ends with success. (2) While the record is waiting, field and label updates are still sent to CR. An update always sends the External System ID CR already holds. (3) The record is checked again whenever workday_id or the CR checklist changes (workflow trigger, still to be set up), by the hourly poller and by the daily sweep. A waiting record is not put on the retry schedule and never goes to the dead-letter queue. (4) Result of the check: CR holds workday_id → success. CR still holds the temporary ID and the checklist is not ticked → waiting. CR still holds the temporary ID and the checklist is ticked → error. The checklist is ticked and workday_id is blank → error. CR holds another value that differs from workday_id → error, and no update is sent. (5) Only that last case stops updates. A blank on either side is not a mismatch. 11/18 — Zeke: the Case check, as it can be built. A read-only check on 11/18 (100 of the 475 production Cases with a CR Client ID) showed that the CR client read does not return the External System ID, and that none of the sampled clients holds its Case record ID. So the integration looks the client up by the Case record ID instead. Found under a different CR ID than HubSpot holds → error, and no update is sent. Found under the same CR ID, or not found → the update is sent. Clients created by hand are therefore not stopped by this rule. Open for production: 81 of the 100 sampled HubSpot Client IDs were not found by the CR client read; to be checked before linked Case updates are turned on.

Open (Zeke, 11/17): confirm whether CR can hold two employees with the same Workday ID, or decide a solution; see section 10. Proposed, not decided: a record that resolves to a CR employee another HubSpot record already holds is marked error and no CR write is made. 11/18 — Zeke: lookup before an employee create. The integration looks CR up by the HubSpot record ID, and also by workday_id when it is filled. Both are read-only. Nothing found → create. Found by the HubSpot record ID → this record's own earlier create: link it (write employee_id), no new create. Found by workday_id only, and another HubSpot employee record already holds that CR employee → error, no CR write. This is decided (11/18) and replaces "Proposed, not decided" above. An unclear answer from CR never leads to a create.

# 2. API rules that will save you debugging time

Agent context [G02] · Use for permissions, sensitive fields, API write constraints, internal option values, and owner lookup.

- Use your own private app token. Our 500+ workflows share one token and already brush against HubSpot's 190 requests per 10 seconds limit. A separate app keeps your sync and our automations from throttling each other, and lets you see your own call logs. Done 

- The child's identity fields are in HubSpot's sensitive-data tier. Child First Name phi_first_name__cloned_, Last Name phi_last_name, Gender phi_gender, Date of Birth phi_date_of_birth, mapped Insurance IDs insurance_id_1 and insurance_id_2, Policy Holder DOB phi__policy_holder_dob, and Diagnosis phi_diagnosis only come back if the app has the sensitive-data scope for deals (crm.objects.deals.sensitive.read, plus .write if you ever write them). Without it they are silently missing from the response. See #11  

- Send internal option values, not labels. Several dropdowns have a value that differs from what staff see. Examples: Case Status shows "Active" / "Inactive" but stores Warm / Cold; Entered Client in CR shows "Yes- Completed" but stores Yes; NY Medicaid - Status shows "Credentialed" but stores Credentialing; BT Entered in Central Reach shows "Yes - Active" but stores Yes; LBA Licensure - NY shows "Will Apply" but stores No; Allergies shows "Yes" / "No" but stores Confirmed / Denial. The appendix lists every mismatch on the fields in this map.   

- Many fields are read-only to the API. Calculated and synced fields reject writes (the whole PATCH fails). On Case: Location location, the staff name fields (supervising_bcba_name, current_primary_bt, current_primary_bt_2), Referral Source referral_source and the total-hours fields. On BCBA and BT: the home address, home city/state/zip, phone and BT gender fields mirror the linked Contact. Everything you write should go to a field flagged writable in this document.   

- Staffing is associations, not fields. Who the Supervising BCBA or Primary BT 1 is lives on the Case to BCBA and Case to BT associations (section 4). Read them with the v4 associations API.   

- Care Coordinator is the Case owner. hubspot_owner_id holds an owner ID. Resolve it to a name and email with GET /crm/v3/owners/{id}  .

- One property has a typo in its internal name: Ongoing Auth period end date is ongoing_autrh_period_end_date.

- Ignore the "F" twins. Fields ending in _f (for example ongoing_auth_period_start_date_f) are the upcoming-auth copies staff fill before a new auth starts. Map the plain field unless Sara wants CR to see the next auth early.  

- Date fields come back as YYYY-MM-DD and must be written as midnight UTC.   

- HIPAA rule on outbound messages: United Care never puts a child's full name in an email or message; staff use Case Initials case_initials. This only matters if anything you build sends notifications.

- A missing property breaks the whole write. If your code writes to a property that is later renamed or archived, HubSpot rejects the entire call. Tell us which properties your integration writes and we will protect them in future clean-ups.

##     Simple explanation

- Webhooks provide speed. One ongoing-update workflow per entity sends record ID and object type when supported source properties change. Keep the three initial enrollment workflows separate.

- Polling provides backup coverage. Recheck linked records and dependencies without stage or original-checkbox restrictions. Test coverage before enabling or reducing polling frequency.

- Azure owns the complete comparison. Centralize mapped values, metadata, labels, explicit blanks, and required relationships in the mapping/comparison configuration. Workflow signals wake that process; they do not duplicate the entire comparison.

- Use workflow triggers, not segment membership, for repeated change signals. A record can remain in a segment through multiple edits without another entry event.
